## 修复前发现的问题

1. **升级顺序**：现有 V40 库默认执行合并后的迁移会因缺少 V27.1、V27.2 校验失败。临时库确认单次 outOfOrder 可补执行；不应直接改写已执行脚本或重编号。实际升级须备份、核对历史，并在补执行后撤掉临时配置。
2. **演示范围不完整**：新库和升级库都初始化 3 场培训，但 audience_type 为旧默认 PUBLIC，名单为 0。当前 TrainingAudienceService 只允许 ALL、DEPARTMENT、USERS，且实际资格依赖名单；演示初始化不能直接跑通学员流程。
3. **用途冗余字段不一致**：新库按顺序执行 V35 可得到 EXAM；V40 库补执行初始化后，3 条培训仍为 STANDALONE，但均关联考试。TrainingService 按 assessment_id 派生用途，PublicLearningController 的培训考试信息接口仍直接读取 purpose，接口口径存在不一致风险。
4. **演示分类不完整**：初始化脚本只设置题库分类，培训本身沿用 UNCATEGORIZED、REQUIRED 和空培训起止时间。数据库允许这些值，但不适合作为分类及培训时段演示的完整样例。
5. **历史考试范围结构**：candidate_scope、assessment_roster、assessment_scope_target 仍在数据库中，本次对主 Java 源码的检索未发现使用。暂不要删除，需确认历史数据与外部查询依赖后另做迁移。
6. **必修自动同步尚未实现**：现有名单缺少任务状态、退出原因及分配来源字段；不能据此宣称支持部门人员变化后的分配和历史保留。

## 后续处理原则

- 部署时核对迁移历史，使用本次受限补迁移策略，不添加全局乱序参数。
- 用后续迁移或明确的初始化流程适配新账号与员工名单模型，不放宽资格校验来兼容演示。
- 用 assessment_id 统一判断培训用途；修复已存在的用途不一致数据，后续再考虑删除冗余字段。
- 演示培训补齐课程分类、时间及学习范围；不制造答题成绩和学习完成记录。
- 必修同步使用独立新迁移，与本次初始化修复分开验收。
